# 从 0 写 CUDA 的方向总结（脱离现有方案）

日期：2026-09-17
对象：Qwen3.8-27B-QUASAR-NVFP4 / 4×V100-SXM2-16GB / PCIe / TP4
模型形状（引自 `config.json` 的 `text_config`）：hidden 5120，**head_dim 256**，
24 个注意力头对 4 个 KV 头（GQA，就是 4 个 KV 头伺候 24 个提问头），64 层。

本文不再沿用之前的方案清单，改从一个问题出发：**180K prefill 的每一秒设备时间
到底去哪了，哪些池离自己的物理上限最远。**

---

## 0. 结论先行

1. **最值得从 0 写的是 prefill 的 NVFP4 融合矩阵乘**，不是通信、不是注意力。
   它是最大的时间池（52.4 s/卡，占 44%），而且是**离本机实测上限最远**的一个
   （跑在本机墙的 44%–59%，而同机纯 FP16 矩阵乘能到 103 TFLOPS）。
2. **注意力（方向 2）是第二位**，但它的对象是 decode 侧（180K 时占 32.9%），
   而且 `head_dim=256` 意味着**所有现成 FlashAttention 都不适用**（上游 FA2 要
   SM80+，FA-Volta 只支持 64/128），所以它天然就是"从 0 写"。
3. **把卡间求和藏进计算（方向 3）**时间池第二大（35.8 s），但同一台机器上
   三次实现尝试全部实测为负，而且"主机阻塞是关键路径"这个假设已被引擎自报数据
   证伪。它只剩一种没试过的形态。
4. decode 侧的逐 token 矩阵乘（GEMV）**不要写**：已到本机显存带宽屋顶的 92.4%。

## 1. 事实基础：180K prefill 的时间去哪了（全部实测）

引自 审计 [54]（nsys 轨迹，device 0，118.2 s 窗口，设备忙 91.8%）：

| 池 | 忙时 | 占比 |
|---|---:|---:|
| NVFP4 矩阵乘（`Kernel2`，即 QPN2/TurboMind 那条路） | 39.8 s | 36.7% |
| 卡间求和（NCCL all-reduce） | 35.8 s | 33.0% |
| 注意力（softmax + block update + head gather） | 13.4 s | 12.4% |
| FP16 矩阵乘（volta_s884gemm 系） | 12.6 s | 10.7% |
| NVFP4 解量化 | 2.1 s | 1.8% |

矩阵乘整条路（NVFP4 + FP16 + 解量化）合计 **52.4 s**。

**离上限多远（实测 + 引自的计算）：**

- 本机墙：独立 cuBLAS FP16 tensor-op 在 M=4096/K=5120 扫 N=512..32768，
  **78.5–104 TFLOPS，约 103 的平台**（引自 审计 [55]，50 次平均）。
- 引擎矩阵乘整条路 **45.6 TFLOPS**，`Kernel2` 单独 **61.0 TFLOPS**
  （引自 审计 [58]，按真实发射形状算的 FLOPs）。
- 也就是整条路在本机墙的 **44%**，单独那个 NVFP4 矩阵乘在 **59%**。
- 排除掉的三个解释（全部实测）：不是形状碎片化（44 chunk × 64 层 × 10 个形状，
  每次都是完整投影）；不是功耗墙（同形状独立跑 97.3 TFLOPS / 1432 MHz / 243 W，
  无降频）；不是 cuBLAS 没开 tensor-op（开关打开后逐项内核数相同，收益 0）。

## 4. 排序理由与第一步

**为什么 #1 排第一**：它是最大的池（52.4 s），而且离物理上限最远（44%–59%）。
相比之下 #3 的池虽然也不小（35.8 s），但同一台机器上三次实现尝试全部实测为负，
继续投入的边际风险高；#1 没有任何一次实测碰过它——之前排除的三个解释
（碎片化、功耗、cuBLAS 开关）全部打在别的假设上。

**#2 排第二**是因为它有明确的实测差距（1.55 倍于地板）且随上下文长度增长
（8K 5.7% → 80K 20.0% → 180K 32.9%，[18]），长上下文正是我们的目标负载。

**第一步（#1）**：写一个最小验证版，只针对 10 个真实形状里最大的那一个，
在独立测试里量"每秒字节数 / TFLOPS"对齐本机墙 103 的百分比。
及格线：**到墙的 60%**（好内核在混合输入下的典型水位，引自 [55] 的说法）。
达不到就停下来报告，不带病接入引擎。

## 6. 事故记录：v5 warp 专业化内核引发设备级 Xid 13（2026-09-17）

### 6.1 事实（观测）

- 本次开机内 Xid **408 条**，时间戳集中在 `[4859.97, 4860.00] s`，进程名
  `nvfp4_fused_ben`，即我正在跑的 v5 测试内核。
- 类型是 **Xid 13「Graphics SM Warp Exception on (GPC x, TPC y, SM z):
  Out Of Range Address」**成簇出现（多个 SM 同时报），紧随其后一条 **Xid 43**
  （通道拆除，`Ch 00000008`）。
- 四张卡**仍在**（`nvidia-smi` 可枚举 4 张），无 `Xid 79/154`，`nvidia-smi` 没有报
  `Unknown Error`。
- 事后复检：四卡 0 MiB / 0% / 40–41 ℃；Xid 最后一条停在 4859.997 s，之后 1300+ 秒
  无新增。
- **不是 `pcie_ipc` 相关**：这个测试只碰单卡，没有多卡通信。

### 6.2 根因（推断，依据是代码）

v5 的做法是 warp 专业化：warp 0–3 专职 mma、warp 4–7 专职装载解量化，用
`stageFlag[2]` 加自旋做生产者-消费者握手。**握手结构本身是成对的**，坏的是装载
循环的索引：

```
for (int e = lid * 32; e < (lid + 1) * aRows * kW; e += 128) {
    int q = e / kW, c = e % kW;
    int r = lid * aRows + (q % aRows);
    q = q / aRows;
    if (q < 1) { sA[b][r][c] = ...; }      // 只有 q<1 才写
}
```

同一份 `e` 被同时当作行偏移和列偏移，`q = q / aRows` 之后只有第一轮为 0，
**其余线程虽然不写 sA，但 `r` 已经越界**；同样的错在 sB 那段里是**无条件写**
（`sB[b][r][c] = v;` 在 `if (q < 1)` 之外），于是直接是共享内存越界写。
落到 SM 上就是 Xid 13 的 "Out Of Range Address"。

### 6.3 为什么 sanitizer 没挡住（我的自检顺序错了）

我先跑的是 `compute-sanitizer`，那次 `exit=124`（超时）。**超时是因为内核自旋
死锁**（装载 warp 与计算 warp 互等），而死锁发生在越界写之后——所以我拿到的是
"超时"，不是"越界"。**教训：对自旋/握手类内核，先跑一次极小的原生启动（不套
sanitizer）看它能否退出，能退出再上 sanitizer 查内存。**

### 6.4 处置

- **不重启、不碰任何卡、不再运行这个版本**。四卡能枚举，属"设备还在"的橙色档，
  不是 `Xid 79/154` 的红色档。
- v5 的源码与二进制已移到 `/tmp/abandoned_v5/`，标记废弃。
- **仓库文件 `src/devices/cuda/sm70/nvfp4_fused_gemm.cu` 不含这段坏逻辑**（grep
  `atomicExch`/`stageFlag`/`isCompute` 无命中），且**没有接入 CMake 构建**，
  所以引擎二进制不受影响。
- 前四轮的可用版本（v2/v3/v4）保留在 `/tmp`，它们都过了 sanitizer 且数值正确。

### 6.5 对结论的影响

**没有推翻任何已测结论**：v2/v3/v4 的实测（15.5–16.9 TFLOPS、跳过解量化后
22.7–27.3 TFLOPS）都是这些版本自己的数，与 v5 无关。**warp 专业化这条路线本身
仍未测到**，因为它在一个有 bug 的实现上失败了，不能据此说这条路线不行。

## 7. 基准形状错了五轮：引擎自报的真实形状（2026-09-17）

### 7.1 怎么发现的

前五轮的独立测试一律用 `M=4096 K=5120 N=5120` 的**方阵**。第 6 轮用引擎自带的形状
直方图（开关 `FASTLLM_NVFP4_PREFILL_CUBLAS=1`，它在 `fastllm-linear-fp8.cu:4031-4068`
里按 `(n,m,k)` 记账并在退出时打印）跑了一次 8K，拿到引擎**自己报的**真实形状：

```
[Fastllm] NVFP4 prefill cuBLAS summary: calls=3072 flops=598.44 TFLOP
  4096x1536x5120   calls=  768  flops= 49.48 TFLOP  flops/call= 64.425 GFLOP
  4096x4352x5120   calls=  768  flops=140.19 TFLOP  flops/call=182.536 GFLOP
  4096x5120x3584   calls=  192  flops= 28.86 TFLOP  flops/call=150.324 GFLOP
  4096x5120x4120   calls=  576  flops= 99.54 TFLOP  flops/call=172.805 GFLOP
  4096x5120x8704   calls=  768  flops=280.38 TFLOP  flops/call=365.072 GFLOP
```

（格式为 `M x N x K`，M=激活行=4096 即 chunk 大小。）

### 7.2 错在哪、影响多大

| | 我一直用的 | 引擎真实的 |
|---|---|---|
| 形状 | 4096 x 5120 x 5120（方阵） | 五种，见上 |
| 主形状 FLOPs 占比 | — | `4096x5120x8704` 占 **46.8%** |
| N（输出维） | 5120 | **8704 / 4352 / 1536 / 5120** |
| K（输入维） | 5120 | **5120 / 3584 / 4120** |

**所以前五轮的"慢 4.4 倍"是拿一个不存在的形状比出来的**，这个结论必须作废重测。

**为什么会错**：我没有从引擎里取形状，而是按 `config.json` 的 hidden/intermediate
**手推**了一个"看起来合理"的方阵。这正是仓库规约里那条"指标的分母分子必须同源"
的同类错误——目标系统的形状是**观测**，我用手推值代替了它。

### 7.3 顺带确认的两件事

1. **这个开关不影响形状的可信度**：`FASTLLM_NVFP4_PREFILL_CUBLAS` 只改"走哪条
   prefill 实现"，`n/m/k` 是调用点给的同一个量；而且默认路径（不开这个开关）最终
   也落到同一段 `FastllmCudaMatMulFloatNVFP4Block16` 的解量化+cuBLAS 兜底
   （`fastllm-linear-fp8.cu:3991-4000` 依次试 QPN2 / TurboMind / Marlin，都不接就
   落到这里）。证据：摘要行 `calls=3072`，与 8K prompt、chunk 4096 的投影数自洽。
2. **有形状不是 128 的整数倍**：`5120x3584` 的 K=3584 是 128 的 28 倍没问题，但
   M=4096 固定整除 128；**N 里最小的 1536 也能整除 128**。所以五种形状都能用
   128x128 分块，不需要边界处理——这是扫描版里那条整除检查的作用。

## 8. 融合矩阵乘路线：上限实测 ≈0，前提被推翻（2026-09-17，12 轮后收口）

### 8.1 决定性测量

在主形状 `M=4096 N=8704 K=5120`（占 prefill GEMM FLOPs 的 46.8%）上，用已验数值的
独立测试把"两步法"拆成两段：

| 配置 | 耗时 | TFLOPS |
|---|---:|---:|
| 解量化 + cuBLAS（引擎现役形态） | 4.445 ms | 82.1 |
| **只跑 cuBLAS（权重预先解量化好）** | **4.469 ms** | 81.7 |
| 差（= 融合能省掉的上限） | **-0.024 ms** | **-0.5%** |

**"融合"能省掉的那部分，在这台机器这组形状上测出来是 0（差值在事件计时噪声内，
且方向为负）。** 也就是说：把解量化融进 GEMM 核里，最好情况等于现在。

引擎侧的天花板也用轨迹算了同一件事（`/home/nsys/pf180k.sqlite`，device 0，118.2 s 窗口）：

```
解量化合计 (FastllmCudaNVFP4Block162HalfKernel) = 2.1 s  = 1.75%
矩阵乘合计 (Kernel2 + volta_*gemm)              = 51.9 s = 43.9%
卡间求和合计 (ncclDevKernel_AllReduce)          = 36.1 s = 30.5%
```

**所以这条路线的收益上限是 1.75%（把解量化整个抹掉），而引擎的对齐次数
（0.437 s / 104 s = 0.42%）就在同一量级。** 要拿到它，必须同时满足两个条件：
解量化全免 **且** 新内核的矩阵乘效率与 cuBLAS 持平。而实测：

| 形状 N×K | 融合内核 | cuBLAS | 比 |
|---|---:|---:|---:|
| 8704×5120（主形状） | 15.3 | 81.2 | 慢 5.3× |
| 4352×5120 | 15.5 | 86.1 | 慢 5.6× |
| 1536×5120 | 12.9 | 84.3 | 慢 6.5× |
| 5120×3584 | 16.3 | 90.4 | 慢 5.5× |
| 5120×4120 | 13.3 | 84.0 | 慢 6.3× |

（cuBLAS 在真实形状上稳定 81–90 TFLOPS，本机墙实测约 103，即**现任实现已在本机墙的
79–88%**。）

### 8.2 结论

**这条路线的前提被推翻，不是实施难度问题。** 前提是"解量化是 prefill 里值得融合掉的
开销"，而实测：

1. 解量化只占窗口 **1.75%**；
2. 把它整个抹掉（预解量化对照）在主形状上省出 **0**；
3. 而 cuBLAS 已经把矩阵乘做到本机墙的 79–88%，留给任何新内核的空间本来就只有 12–21%。

**所以即使写成一个完美的融合内核，上限是 1.75%，且必须先把 mma 效率从当前水平
拉高 5 倍以上才能谈不亏。** 12 轮里已实现的部分（内核可用、数值正确、过 sanitizer）
保留在 `src/devices/cuda/sm70/nvfp4_fused_gemm.cu`，**未接入构建、默认不影响引擎**。

### 8.3 12 轮里我犯的错（逐条留痕）

1. **基准形状错了 5 轮**：一直用 `4096×5120×5120` 方阵，而引擎真实是五种形状、
   主形状输出维是 8704。手推形状代替了引擎自报的形状。
2. **`cublasGemmEx` 的 `alpha/beta` 传成 `__half`**：`CUBLAS_COMPUTE_32F` 要求 `float`，
   传错后 C 全为 0，表现为"超差 99.98%、`max_rel` 恰好 = 1.0"——而 `max_rel == 1`
   正是"C 全 0"的签名。我据此得出的"语义是错的"结论作废。
3. **容差定得比 fp16 累加本身的误差还严**：CPU 模拟显示 K=5120、量级 55 时纯 fp16
   累加天然超差 7.4%，我却用 `0.05|ref|+0.02` 去卡，把正确的基线判成了错的。
4. **两次打坏设备**：v5（warp 专业化，索引越界，Xid 13 ×408 条）与
   `verify2step`（cublas `ldc=N<M`，越界写，Xid 31 ×5 条）。
5. **归属判断错了两次**：先把 Xid 31 归给"更早的运行"（实为最后一次扫描），
   后又把根因归给"半修的列主序版"（实为已被换掉的行主序版）。

**最该早做而没早做的一件事**：先用确定性小例子（M=2/K=3/N=2）把 cublas 的
`(语义, 尺寸, 步长)` 三元组在 CPU 上对齐，再上机。这条如果第 5 轮就做，能省掉
后面 6 轮的反复。
