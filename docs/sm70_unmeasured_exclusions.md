# 哪些优化方向被"划掉了"，但其实没在这台机器上真正量过（2026-09-17）

**一句话结论**：有 **9 条**方向在文档里被写成"不做/排除"，但排除它们的理由**不是**在这台机器上跑出来的结果，而是探针、估算、"没有本机数字"这类依据。这些方向的准确状态是 **"没做过、没数据"**，不是"已经证明不行"。

**为什么要写这份东西**：项目里"排除"这个词用得太随便。有的排除是**真的在这台机器上开/关各跑一次比出来的**（可信，不用再翻）；有的只是**别人文档里的估计、或者自己捏的小程序测的数字**。这两种混在一起，会让后来的人（包括我自己）以为一条路已经死了——其实只是**没人量过**。

## 0. 怎么用这份文档

- **第一张表** = 划掉了但**没在这台机器上量过**的方向，这是本文的主体，按"现在能不能测"排序。
- **第二张表** = **真的量过、才划掉的**，列出来只为了对照，不要再翻。
- 每条"依据"栏写的是**原文出处**（`文件:行`），不是我的转述。
- 按项目规矩，第一张表里那些方向的准确说法是 **"没做、无数据"**，**不许**写成"已经否掉""不值得做"。

### 1.1 第 9 条要展开说，因为它是文档里最容易被误读的一条

`backlog:126` 的标题是"明确划出范围（**不做，且理由已被实测钉住**）"，里面列了
"fused AllReduce+RMSNorm"。但本会话的实测（`.audit`）是：

- device 0 全 180K prefill 的算子相邻普查：`ADD→NORM` 直接相邻 = **0 次**，
  而 `ADD→AR` = 6656、`AR→NORM` = 6652。

也就是说，**"把残差加法和 RMSNorm 融在一起"这个形态在这份图里根本不存在**
（它们被 all-reduce 隔开了）。这否掉的是**那个形态**，不是"减少 norm 这一趟"这件事。
真正可能的一条是"把输入 RMSNorm 融进 NVFP4 的 prefill GEMM"——而它**从未测过**，
且它的上限很小（转换类内核合计 0.028 s，norm 一趟 0.75 s），见 `sm70_4x200k_rotate_plan.md`。

## 3. 第 1 条的执行记录（因为它是唯一一条本机能测的）

2026-09-17：按上面的分析动手实现 TP4 push AR。

- **实现**：新增 `FastllmCustomAllReducePushKernel<T, UsePdl, Rank>`
  （`src/devices/multicuda/fastllm-custom-allreduce.cu`），把 TP2 的 PushAdd 机制
  推广到 4 rank、去掉 residual 语义、**FP32 按 rank 序累加后一次 downcast**
  （与现役 one-stage 的 `upcast → sum(ptr[0..3]) → downcast` 逐位一致，
  而不是 TP2 那个用 `__hadd` 的 fp16 累加）。
- **接线**：env `FASTLLM_CUDA_CUSTOM_ALLREDUCE_PUSH4`（默认 **off**）+
  `CustomArUsePush4` 资格门（4 rank、`bytes < 40 KiB`、16B 对齐、workspace 就绪）
  + `LaunchCustomArPush4` 派发。
- **状态**：编译通过；回归测试结果见 `.audit`（跑完补记）。
